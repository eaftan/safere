# Testing

SafeRE has an extensive test suite organized into several layers: unit
tests for internal components, integration tests using RE2's reference
test data, cross-engine tests comparing against `java.util.regex`,
regression tests for specific bugs, and functional tests for the public
API. Many tests are parameterized using reference data originally generated
by RE2 C++ and obtained via RE2/J. Run commands from the repository root.

## Test organization

Library tests live in [safere/src/test/java/org/safere](../safere/src/test/java/org/safere/).
Choose the relevant behavioral suite rather than treating this guide as an
exhaustive list of test classes.

| Layer | Purpose and starting points |
|---|---|
| Public API | `PatternTest`, `MatcherTest`, and `PatternSetTest` exercise user-visible operations. |
| Components | Tests beside the parser, compiler, AST, character classes, and individual engines check internal contracts. |
| Reference data | `RE2SearchTest`, `RE2FindTest`, and `RE2ExhaustiveTest` consume inherited test vectors; provenance is recorded below. |
| JDK comparison | `CrossEngineTest`, `CrossEngineExhaustiveTest`, and `RandomTest` compare supported behavior with the JDK. |
| Engine equivalence | `EnginePathEquivalenceTest` and `Utf8EnginePathEquivalenceTest` exercise forced paths. |
| State transitions | `MatcherStateMachineTraceTest` and `Utf8MatcherStateMachineTest` exercise sequences of public operations. |
| Regression matrices | Suites such as `QuantifiedCaptureSemanticsTest` and `GraphemeRegionCompatibilityMatrixTest` cover behavioral classes. |
| Complexity | Work-counter and scaling tests check bounded matching, decoding, and allocation work. |
| Repository policy | Tests such as `LicenseHeaderTest` check source and test-harness conventions. |
| Offline differential sweeps | `safere-exhaustive` enumerates bounded grammars and input matrices, records divergences, and replays findings. |

Use [safere-crosscheck](../safere-crosscheck/README.md) for generated public API
comparisons, [safere-fuzz](../safere-fuzz/README.md) for Jazzer, and
[safere-exhaustive](../safere-exhaustive/README.md) for offline sweeps.

## Tests Ported from RE2 and RE2/J

A significant portion of SafeRE's integration test suite is ported from
the RE2 family of libraries.  This was an intentional strategy: by reusing
established test data and test cases, we retain coverage of core automata
behavior. Java compatibility and documented intentional divergences take
precedence where SafeRE's contract differs from RE2.

### Test Data Files

The test data files in `safere/src/test/resources/` were taken from
[RE2/J](https://github.com/google/re2j)'s
[`testdata/`](https://github.com/google/re2j/tree/master/testdata)
directory.  RE2/J in turn obtained them from the
[RE2](https://github.com/google/re2) C++ project, where they were
generated by RE2's exhaustive test infrastructure.

| File | Origin | Description |
|---|---|---|
| `re2-exhaustive.txt.gz` | RE2 C++ (via RE2/J) | Systematically generated (pattern, text, expected) tuples covering all operator combinations |
| `re2-search.txt` | RE2 C++ (via RE2/J) | Search test vectors with full-match, partial-match, and submatch results |
| `basic.dat` | AT&T POSIX (via RE2/J) | AT&T POSIX basic regex test data |
| `nullsubexpr.dat` | AT&T POSIX (via RE2/J) | AT&T POSIX null subexpression tests |
| `repetition.dat` | AT&T POSIX (via RE2/J) | AT&T POSIX repetition tests |

### Test Code Ported from RE2/J

[RE2/J](https://github.com/google/re2j) is a Java port of RE2.
The following test code was ported from RE2/J and adapted to SafeRE's API
and test framework (JUnit 6 + AssertJ):

- **`RE2FindTest`** — Find/match test data from RE2/J's `FindTest.FIND_TESTS`.
  Adapted to compare matched text instead of byte offsets, since SafeRE
  exposes UTF-16 indices through its String API.
- **`RE2ReplaceTest`** — Replace test cases from RE2/J's `RE2ReplaceTest`.
- **`RE2ExhaustiveTest`** — Test runner ported from RE2/J's `ExecTest`
  (itself ported from Go's `regexp/syntax/exec_test.go`).  Parses
  `re2-exhaustive.txt.gz` and runs each test case.
- **`RE2SearchTest`** — Test runner ported from RE2/J's `ExecTest`.
  Parses `re2-search.txt`.
- **`RE2PosixTest`** — Test runner ported from RE2/J's `ExecTest`.
  Parses the AT&T `.dat` files.
- **`PatternTest`** (subsections) — Compile validation, group counting, and
  `quote()` round-trip tests from RE2/J's `RE2CompileTest`,
  `RE2TestNumSubexps`, and `RE2QuoteMetaTest`.
- **`UnicodeTablesTest`** (subsection) — `simpleFold()` tests from RE2/J's
  `UnicodeTest`.

### Test Code Ported from RE2 C++

The following test code was ported from the C++ RE2 test suite and
rewritten in Java:

- **`RE2RegressionTest`** — Bug regressions and edge cases from
  `re2_test.cc`.
- **`SimplifierTest`** — Simplification tests from `simplify_test.cc`.
- **`RandomTest`** — Random/fuzz testing approach from `random_test.cc`,
  adapted to compare against `java.util.regex` instead of PCRE.
- **`PatternSetTest`** (subsection) — Set tests from `set_test.cc`.

## Running Tests

Reserve exclusive machine access for tests, including tests in other worktrees.
The runner waits for the current workload to finish; see
[exclusive machine access](DEVELOPMENT.md#exclusive-machine-access).

```bash
# Run all tests
./tools/machine-run -- mvn test -pl safere

# Run a specific test class
./tools/machine-run -- mvn test -pl safere -Dtest=ParserTest

# Run tests with coverage report (JaCoCo)
./tools/machine-run -- mvn verify -pl safere -Pcoverage

# Run crosscheck module tests
./tools/machine-run -- mvn test -pl safere-crosscheck -am

# Run SafeRE tests and generated public API tests through the crosscheck facade
./tools/machine-run -- mvn verify -pl safere,safere-crosscheck -am -Pcrosscheck-public-api-tests

# Run generated public API tests only, after safere and the parent POM are installed locally
./tools/machine-run -- mvn verify -pl safere-crosscheck -Pcrosscheck-public-api-tests

# Run Jazzer fuzz targets in regression mode
./tools/machine-run -- mvn test -pl safere-fuzz -am
```

Coverage reports are generated at
`safere/target/site/jacoco/index.html`.  Note that JaCoCo is disabled
by default; the `-Pcoverage` profile is required to enable it.

## Compile and Cold-Start Benchmarks

Compile and cold-start workloads are selected from the declarative plan:

```bash
# Run every declared execution profile with the standard schedule.
./run-java-benchmarks.sh --declared

# Smoke representative plan-selected trials across execution profiles.
./run-java-benchmarks.sh --smoke --declared
```

`compileOnly` declarations measure steady-state per-compile work after
initialization. `singleShotColdStart` declarations use a fresh fork and retain
the first-use cost seen by short-lived processes. Do not combine those timing
groups.

## Differential Testing with safere-crosscheck

The [safere-crosscheck](../safere-crosscheck) module provides a
differential-testing facade that runs both SafeRE and `java.util.regex` on
covered operations, comparing results and throwing `CrosscheckException` if they
diverge. This catches behavioral differences that aren't directly covered by
unit tests.

To use it, change your import from `org.safere.Pattern` to
`org.safere.crosscheck.Pattern` (and likewise for `Matcher`). Consult the
module README for compared operations and methods that only delegate.

The facade records matcher calls in a trace. When a divergence is detected,
the exception includes the full trace, providing enough context to reproduce
and report the bug. See
[safere-crosscheck/README.md](../safere-crosscheck/README.md) for details.

Select validation for the changed behavior as described in [AGENTS.md](../AGENTS.md).
The combined reactor command runs library tests and generated public API tests
through the crosscheck facade when broader coverage is warranted. The `-am`
flag rebuilds the local library instead of resolving a stale installed artifact.

## Fuzz Testing with Jazzer

SafeRE is continuously fuzzed by [OSS-Fuzz](https://google.github.io/oss-fuzz/).

The [safere-fuzz](../safere-fuzz) module contains broad and strict JDK differential
targets, property/model checks, and robustness checks. The
[fuzzing policy](../safere-fuzz/TARGETS.md#policy) defines their failure and enrollment
rules. Hosted OSS-Fuzz runs only targets enrolled in the
[target manifest](../safere-fuzz/targets.json); exploratory targets are not
automatically enrolled. They do not depend on the crosscheck facade. By default,
they run in regression mode over checked-in seed inputs:

```bash
mvn -pl safere-fuzz -am test
```

For coverage-guided fuzzing, set `JAZZER_FUZZ=1` and select a single target:

```bash
JAZZER_FUZZ=1 mvn -pl safere-fuzz -am -Dtest=MatchFuzzer \
  -Dsurefire.failIfNoSpecifiedTests=false test
```

When a fuzzer finds a valid SafeRE/JDK divergence or crash, minimize the input
and add a normal JUnit regression test before fixing the bug. See
[safere-fuzz/README.md](../safere-fuzz/README.md) for target descriptions and
workflow details.

## Exhaustive differential testing with safere-exhaustive

The [safere-exhaustive](../safere-exhaustive/README.md) module runs deterministic
comparisons against `java.util.regex` over generated pattern, input, flag, and
matcher-state combinations. Each sweep is exhaustive over its declared bounded
matrix, not over all possible regexes. Use it to investigate a behavioral class
or validate changes that affect parser or matching invariants.

These sweeps are explicit command-line tools, separate from the library's
JUnit reference-data tests and coverage-guided Jazzer fuzzing. An ordinary
`mvn test` does not run their full matrices. Start with an affected range or
saved examples; run a complete matrix when the change's scope or unresolved
risks warrant broader validation.

### Choosing a sweep

| Area | Sweep classes |
|---|---|
| Character-class syntax and control escapes | `CharacterClassDivergenceSweep`, `ControlEscapeDivergenceSweep` |
| Unicode membership and case folding | `UnicodeCharacterClassDivergenceSweep`, `CaseFoldingCharacterClassDivergenceSweep` |
| Scalar consumption at region boundaries | `RegionScalarDivergenceSweep` |
| Empty matches, assertions, and region bounds | `RegionZeroWidthDivergenceSweep` |
| Grapheme clusters and boundaries | `GraphemeClusterDivergenceSweep` |
| Repeated zero-width quantifiers and captures | `ZeroWidthQuantifierDivergenceSweep` |
| DFA range narrowing and leftmost match selection | `DfaSandwichLeftmostStartDivergenceSweep` |

The module README describes each matrix and its compatibility exclusions.

### Running and expanding a sweep

Use the dispatcher, which builds the module and its dependencies and supplies
the runtime classpath:

```bash
./run-exhaustive-sweep.sh CharacterClassDivergenceSweep --range=:1000000 \
  --output-dir=target/exhaustive-reports/character-class-check

./run-exhaustive-expander.sh \
  --input-dir=target/exhaustive-reports/character-class-check
```

`--range=start:end` selects a half-open range of generated case indices. Either
bound may be omitted; omit `--range` to run the complete matrix. `--threads=N`
controls sweep workers. Use a fresh output directory for each generated run:
the sweep refuses to overwrite an existing compact archive. Keep generated
reports under `target/` and out of Git.

Generated runs checkpoint `run-manifest.json`, `progress.json`, and compact
per-worker divergence indices. After completion or interruption, expand the
archive and inspect `expanded/class-counts.tsv` and the resulting JSONL files.
By default, the expander materializes all `UNKNOWN` and `EXPECTED_ZERO` findings
and bounded samples of `KNOWN_INTENTIONAL` findings; exact counts remain
available for every class. An interrupted archive is useful evidence, but does
not establish that the requested matrix completed.

### Reviewing and replaying findings

- `EXPECTED_ZERO` identifies a known bug class that should have no findings.
- `UNKNOWN` needs investigation and classification.
- `KNOWN_INTENTIONAL` must agree with the documented
  [compatibility boundary](../INTENTIONAL_DIVERGENCES.md); inspect representative
  traces rather than trusting the label alone.

Minimize actionable examples and add systematic regression coverage before
fixing the behavior. After a fix or classifier change, replay affected JSONL
files through the same sweep using `--replay-file=path/to/expanded-examples.jsonl`
and a separate `--output-dir`. Recheck those findings before repeating a large
matrix. Preserve the sweep revision and JDK version when comparing reports,
since generated case indices and the JDK oracle can change.

See the module's [full review procedure](../safere-exhaustive/README.md#full-sweep-review-procedure)
for expansion options, classification review, and auditing known-divergence
buckets from older archives.

## Choosing an oracle

Use the JDK for comparable public behavior, forced engine paths for internal
equivalence, and explicit expected values for approved SafeRE divergences.
Keep exact JDK implementation observations separate from SafeRE requirements.
`@DisabledForCrosscheck` needs a specific reason: SafeRE-only APIs, internal
invariants, deliberate divergences, and already-differential tests have different
oracles. Changes to test generation must preserve discovery and exclusion policy.

Test operation sequences as well as isolated results: captures, snapshots,
replacement, region changes, bounds changes, and subsequent `find()` calls can
expose state errors. See [semantic invariants](INVARIANTS.md).

Use deterministic work counters or stable scaling comparisons to check linear
work. Fixed elapsed-time thresholds are unsuitable correctness oracles.

## External UTF-8 integration validation

Validate an adapter in its host project's regex suite, covering matching,
extraction, split-style iteration, replacement, error translation, and engine
configuration. Include multibyte input, empty matches, nonparticipating captures,
and nonzero-offset input windows. Follow the
[external validation workflow](DEVELOPMENT.md#external-project-validation).

The [historical Trino measurements](benchmarks/TRINO_UTF8.md) record a local
integration experiment; use the host project's current test names and build
requirements when repeating validation.

## Vector compiler stress

`TeddyVectorScanTest` directly checks the experimental Teddy kernel with alternating
stage counts, misses, candidate-heavy input, nonzero array offsets, search starts,
and vector/tail boundaries. It runs when the Vector provider is enabled:

```bash
mvn -pl safere -Pvector-tests -Dtest=TeddyVectorScanTest test
```

`TeddyVectorScanStress` is a separate diagnostic entry point for the C2 failure in
[SafeRE #1170](https://github.com/safere/safere/issues/1170). It warms three-byte
models before introducing two-byte models and checks each scan result. Run it in
fresh JVMs on an x86-64 AVX2 machine with an affected JDK 25 or 26. Build using the
project build JDK first:

```bash
mvn -pl safere -Pvector-tests -DskipTests package
/path/to/affected-jdk/bin/java --add-modules=jdk.incubator.vector \
  -XX:UseAVX=2 -XX:+UnlockDiagnosticVMOptions \
  -XX:+StressIncrementalInlining -XX:+StressGCM -XX:+StressLCM -XX:+StressIGVN \
  -XX:StressSeed=5 -XX:-CreateCoredumpOnCrash \
  -XX:ErrorFile=/tmp/teddy-hs_err_pid%p.log \
  -cp 'safere/target/test-classes:safere/target/safere-1.2.0-SNAPSHOT.jar' \
  org.safere.TeddyVectorScanStress
```

The diagnostic flags are HotSpot-specific and are not supported on every JDK.
Repeat with varied `StressSeed` values, preserving the exact JDK, commands, exit
statuses, output, and crash logs. Compare unpatched and patched production JARs
with the same compiled driver, seeds, flags, and hardware. Establish crashes in
the unpatched control before treating passing patched runs as evidence. Check
that crashes have the expected C2 Teddy frame and null payload fault; other
failures need separate diagnosis.

For representative seeds, add `-XX:+PrintCompilation -XX:+PrintIntrinsics` and
`-XX:CompileCommand=option,org.safere.TeddyVectorScan::indexOfTeddyUtf8,PrintInlining`
to verify that C2 compiles the kernel and intrinsifies its vector operations.
Stress passes complement the source invariant that disabled-stage vector operands
are non-null; neither ordinary CI passes nor a finite stress campaign alone proves
absence of a compiler bug. Keep these diagnostic flags out of the default suite.
